# agent-智能体设计

## 一、面试总纲：先分场景，再讲机制

**面试官可能怎么问：Agent 是不是就是大模型加工具调用？**

答题要点：
- 基础 Demo：可以理解为大模型加工具调用，开发者给工具列表，模型选工具、传参数、拿结果。
- 工业级 Agent：要有感知、规划、行动、反思的闭环，核心模块包括记忆、规划、工具调用、反思迭代、异常终止、评测。
- 判断标准：看有没有自主决策闭环，能不能在生产环境可控运行。
- 常见误区：堆一堆工具就自称 Agent，实际处处需要人工兜底。
- 通用答法：先分 Demo 级和生产级，再讲机制，再讲风险边界，最后落到评测和成本。

## 二、Agent 核心定义与能力模块

| 模块 | 作用 | 面试要点 |
|---|---|---|
| 记忆 | 短期上下文记忆加长期知识库记忆 | 解决模型忘事，是持续完成复杂任务的基础 |
| 规划 | 把复杂任务拆成多步并排执行顺序 | 遇到异常能动态调整路径 |
| 反思迭代 | 执行后自检结果，错了回溯重试 | 尽量无需人工介入 |
| 工具调用 | 调用搜索、数据库、代码执行、第三方 API | 只是执行环节，不等于完整 Agent |
| 闭环 | 感知、规划、行动、反思 | 判断工业级 Agent 的核心 |

**面试官可能怎么问：工业级 Agent 和 Demo 级怎么区分？**

答题要点：看闭环、异常处理、评测体系、成本控制、权限安全。Demo 通常只覆盖工具调用，生产级要能扛住多步任务、失败重试和结果校验。

## 三、上下文与记忆管理

### 1. 多轮对话必须保留全部上下文吗

**面试官可能怎么问：Agent 处理多轮对话，历史要全部保留吗？**

| 场景 | 做法 | 结果 |
|---|---|---|
| 默认基础模式 | 把完整对话历史拼接成 Prompt 送入模型 | 必须保留，否则丢失上下文、答非所问 |
| 开启摘要压缩 | 对长对话、低信息密度历史做摘要 | 减少冗余历史占用窗口和推理成本 |
| 开启分层记忆和重要性筛选 | 核心事实、关键决策、任务所需信息留在活跃上下文，次要寒暄归档长期记忆按需召回 | 可以不保留全部上下文，仍维持连贯性 |

答题要点：
- 先分默认模式和优化模式，再讲机制。
- 判断依据是对话信息密度、任务复杂度、记忆筛选与召回机制。
- 风险：重要性判断和召回机制没做好就裁上下文，会关键信息丢失、前后回答矛盾、任务执行中断。长周期任务、多轮复杂对话风险最高。

### 2. 上下文窗口怎么突破

**面试官可能怎么问：长任务把上下文窗口撑爆了怎么办？**

答题要点：
- 传统 RAG 和摘要压缩有局限：一次会话写大项目会 token 耗尽留下烂尾；开新会话会离散失忆；代码类任务压缩摘要容易丢关键变量、版本依赖。
- 工业方案是“环境即记忆”：持久化日志、Git 仓库、TodoList 文件，把记忆外挂到文件系统。
- 双阶段智能体：初始化 Agent 搭脚手架、配环境、初始化 Git、建进度表；编码 Agent 增量循环，读状态、写一个功能、跑测试、Git 提交、清空上下文。
- 三原则：环境即记忆；串行优于并行；测试驱动。
- 收益：把无限长任务切成短小干净片段，token 可控。

### 3. 长期记忆存错了怎么修

**面试官可能怎么问：Agent 长期记忆里有一条错误操作经验，怎么修正？**

答题要点：
- 先区分事实记忆和程序性记忆。程序性记忆是“怎么做事的偏好和流程”，错误更隐蔽，会让 Agent 每次走同一条错误路径，而且看起来自洽。
- 写入前：做过滤和外部证据交叉验证，只允许带工具名、带错误原因的可执行内容沉淀。
- 存储时：带来源会话、时间戳、版本、置信度；做冲突检测，用语义匹配抓真矛盾；做过期检测，源文件改了立即失效，超期未引用降权。
- 修正时：用生命周期“假设、启用、验证、作废或被替代”。旧条目标记作废，新增替代条目并指向旧条目，默认召回新条目，保留审计记录。
- 常见误区：发现错了直接覆盖删除。这样会失去对错误本身的记忆。让 Agent 自己管理记忆还可能先删审计痕迹。

### 4. 记忆系统怎么省 token

**面试官可能怎么问：每轮都调大模型判断是否要记忆，token 成本太高怎么办？**

答题要点：
- 不要每轮都调用大模型判断，可按会话结束、轮次触发、事件驱动提取。
- 记忆分层，活跃上下文只放核心信息，历史归档到向量数据库按需召回。
- 工具按需加载，避免一次注入全部工具。
- 成本和效果要量化，用固定测试问题对比修改前后结果。

## 四、ReAct 与规划执行

### 1. ReAct 是什么，怎么画

**面试官可能怎么问：现场画一下 ReAct Agent，代码层面有哪些模块？**

答题要点：
- ReAct 等于 Reasoning 加 Acting，2022 年 Google 论文提出，核心循环是 Think、Act、Observe，循环到任务完成或触发终止。
- 只答三段循环只能保底。工程答法要落到五个模块。

| 模块 | 职责 |
|---|---|
| 模型客户端 | 协议对接、结构化输出解析 |
| 工具注册表 | schema 声明、参数校验 |
| 工具执行器 | 真正调用函数、处理超时与重试 |
| 循环控制 | 解析 Action、拼接 Observation、判断终止 |
| 上下文管理 | 历史裁剪与压缩 |

- 边界要讲清：解析 Action 和拼 Observation 归循环控制。
- 终止条件：最大轮数、token 预算、wall-clock 超时、输出 Final Answer，四者满足其一即退出，统一收敛在循环控制。
- 异常处理：工具级异常在执行器内捕获并重试，整体失败上升到循环控制做熔断。
- 局限：一步一步走，错误会沿上下文累积；token 膨胀快；步骤多、依赖复杂时应切换到 Plan-Execute。

### 2. ReAct 和 Plan-Execute 怎么选

**面试官可能怎么问：什么时候不用 ReAct？**

答题要点：ReAct 适合步骤少、环境反馈驱动、需要边做边调整的任务。Plan-Execute 适合步骤多、依赖复杂、需要先出计划再逐步执行并允许回看重新规划的任务。ReAct 的错误累积和 token 膨胀是主要局限。

### 3. Planner、Executor、Critic 是什么

**面试官可能怎么问：Planner、Executor、Critic 在 Agent 架构里怎么实现？Critic 有什么用？**

答题要点：Planner 负责拆解和规划，Executor 负责执行工具和动作，Critic 负责评估结果并触发修正。Critic 用于自我校验。某些场景不直接用 ReAct，因为错误累积和成本高，可改用 Plan-Execute 或规则校验。

## 五、工具、MCP 与 Skill 路由

### 1. MCP 和工具调用差在哪

**面试官可能怎么问：MCP 和 Function Calling 有什么区别？**

| 对照维度 | 工具调用 | MCP |
|---|---|---|
| 所属层次 | 模型或应用层的调用机制 | 连接工具与模型的协议层 |
| 解决的问题 | 模型如何发起一次工具调用 | 工具如何标准化接入与复用 |
| 复用性 | 通常与应用绑定，换应用需重接 | 工具一次实现，多客户端复用 |
| 一句话 | 让模型会调工具 | 让工具能被任何支持 MCP 的客户端调 |

答题要点：MCP 服务端工具最终仍由模型以工具调用形式触发。可补 Host、Client、Server 角色划分。

### 2. 工具必须预先定义吗

**面试官可能怎么问：Agent 可调用的工具必须开发时预先定义吗？**

| 模式 | 做法 | 适用场景 | 前提 |
|---|---|---|---|
| 静态工具注册表 | 框架维护工具名、入参格式、功能描述，不在表里模型不知道也无法正确调用 | 安全优先的生产场景 | 默认模式 |
| 插件式热注册 | 运行时热插拔接入新工具，无需重启 Agent 服务 | 业务迭代快、频繁对接新系统 | 插件机制 |
| 代码生成式自构建 | Agent 自己生成工具函数、校验可用性、自动注册并调用 | 开放式科研 Agent、通用任务 Agent | 代码生成权限加隔离沙箱 |

答题要点：判断能否动态扩展，看安全边界、插件机制、沙箱执行环境。风险是代码执行越权、系统安全漏洞、异常执行崩溃。

### 3. 装了 100 个 Skill 为什么还选错

**面试官可能怎么问：Agent 配了很多 Skill，为什么还是选错或走错流程？**

答题要点：问题常在路由，不在 Skill 数量。用四路口排查。

| 路口 | 核心问题 | 修法 |
|---|---|---|
| 可见性 | Agent 能不能看见正确 Skill | Agent 先看名称和 description，命中才读 skill.md；清单过长 description 可能被压缩，Codex 中部分 Skill 还可能被省略 |
| 职责冲突 | 多个相关 Skill 选哪一个 | description 写太小会表达重叠、名异实同、范围过宽；用起点和交付物划边界，并写在 description 前面 |
| 可执行性 | 选中后能不能真正执行 | 每个 Skill 写职责编件卡 |
| 路由测试 | 怎么证明它真的会选 | 用真实任务做路由测试 |

职责编件卡七项：解决什么任务；什么时候用；什么时候不用；需要哪些输入；交付什么结果；缺条件时该追问、降级还是停止；高风险场景的额外约束。

高风险动作如设计、发布、部署、付款，建议设 `allow_implicit_invocation=false`，只允许用户显式触发。

路由测试至少覆盖五类任务：直接命中、近义表达、边界任务、同时匹配、不应触发。观察两个维度：有没有选中；选中后是否按合同交付。对照实验用同一任务、同一模型、同一上下文。

多 Skill 同时调用不一定是错，但要指定一个主编排者，写清执行顺序、上下游输入输出、最终验收，材料不足时也要有人负责停下来。

### 4. Skill 选型看什么

**面试官可能怎么问：怎么选 Agent Skill？**

答题要点：安装量只是热度参考，使用前看说明、更新和示例。按能力分层选：原型生成层、架构工程层、体验打磨层。推荐组合可作示例：develop-web-game 加 game-engine 加 game-feel。不要只看排名。

## 六、多 Agent 协作与一致性

### 1. 多 Agent 并发怎么保证最终一致性

**面试官可能怎么问：同一个复杂任务拆给多个 Agent 并发执行，怎么保证最终协作结果一致？**

答题要点：
- 先定义一致性：全局任务结果正确、状态统一、无重复操作、无数据冲突。
- 先列失效场景。

| 失效场景 | 后果 |
|---|---|
| 任务拆分粒度不当导致语义重叠 | 多个 Agent 重复执行同一段业务 |
| 部分 Agent 失败后重试 | 已成功子任务重复执行，产生脏数据 |
| Agent 间通信延迟、共享数据读写竞争 | 写覆盖冲突 |
| 调度中心宕机、任务状态丢失 | 任务重发或漏发 |
| 异构 Agent 协议不统一、结果格式不兼容 | 结果无法正确汇总 |

- 三层框架：第一层明确一致性范围和失效场景；第二层用全局任务状态机加子任务幂等加最终一致性补偿，辅以语义去重、乐观锁、调度高可用、结果校验、数据库唯一约束；第三层做生产异常处理。

落地设计：
- 任务表字段：GlobalTaskID、SubTaskID、AgentID、TaskStatus、ExecuteResult、CompensateStatus。
- 语义去重：拆分前做语义分块去重，每个子任务生成唯一语义指纹，分配前先插入记录，插入成功才执行，插入失败返回已有结果。
- 状态机：再拆分、执行中、汇总中、已完成或补偿中、已失败。每次状态变更基于当前状态用乐观锁更新，第一条请求成功，第二条并发请求影响行数为 0。
- 子任务幂等：失败重试不产生重复效果，避免重复扣费、重复写入。
- 生产细节：异构 Agent 建独立协议适配层，统一封装幂等接口与结果格式，不侵入 Agent 原生逻辑；全局状态与子任务记录写同一数据库事务；完成超 7 天可归档，但保证归档期间没有失败重试；监控任务重复率、状态冲突率、补偿成功率、调度可用性；降级为单 Agent 串行执行加人工对账，并做最终结果校验。

常见误区：只做调度中心加重试加锁，不做语义校验、幂等、补偿、异构适配。

### 2. 多 Agent 必要性怎么答

**面试官可能怎么问：为什么不用一个 Agent，非要用多 Agent？**

答题要点：先讲单 Agent 瓶颈，包括上下文过载、职责耦合、难独立评测、复杂任务串行慢。再讲多 Agent 收益，职责分离、并行、独立评测。再讲代价，重复工作、协调一致性、成本上升。主 Agent 做 plan 后，要明确子 Agent 边界和交付物，避免子 Agent 重复写计划或做已做过的事。主 Agent 与子 Agent 的基模可按成本和能力分层选型。

## 七、Harness、安全、并发与性能

### 1. Agent 跑偏不只怪模型

**面试官可能怎么问：Agent 漏步、跑偏、循环打转，是模型问题吗？**

答题要点：用 Harness Engineering 回答。Harness 是模型周围的环境、工具、规则、流程和反馈。Harness Engineering 是设计这些约束与引导，让模型沿明确路径完成任务。它不等于写提示词，关心任务怎么拆、结果怎么验、出错怎么停、规则怎么更新。

| 都江堰类比 | Agent 设计动作 |
|---|---|
| 鱼嘴分流 | 任务拆解、子任务边界与交付衔接 |
| 宝瓶口控水 | 过程约束加结果约束、验收条件 |
| 飞沙堰泄洪排沙 | 中止、超时、降级、人工关卡 |
| 历代维护扩建 | 基于失败记录的反馈与规则更新 |

答题要点：过程约束规定每一步能读什么、能调用什么、不能越过什么边界。结果约束规定输出必须具备哪些字段、文件、证据和验收条件。异常设计包括次数上限、超时、工具失败保留现场、转人工、降级。维护要基于真实失败记录调整规则，删除过时或冲突上下文，用新任务验证改动。

### 2. Agent 安全为什么从 Prompt 走向 Runtime

**面试官可能怎么问：Agent 安全和 Prompt 安全有什么区别？**

| 层面 | 关注点 | 手段 | 局限 |
|---|---|---|---|
| Prompt 层 | 输入侧，提示词注入、越狱、敏感指令诱导 | 过滤、改写、模型侧对齐 | 管不住工具调用、代码执行、文件网络访问、多步任务链 |
| Runtime 层 | Agent 运行时的实际行为 | 工具权限最小化、调用链审计、沙箱隔离、异常行为拦截、高风险动作人工确认 | 需要系统工程能力 |

答题要点：核心是从“管住说什么”扩展到“管住做什么”。面试要讲清 Prompt 安全和 Runtime 安全的区别与联系。

### 3. Agent 太慢，TTFT 怎么优化

**面试官可能怎么问：大模型推理慢，怎么设计异步和流式架构，把首字响应时间 TTFT 压到极致？**

答题要点：按四层回答。

| 层级 | 做法 |
|---|---|
| 协议层 | 流式输出，优先 SSE，并说明为什么选 SSE 而不是 WebSocket |
| 逻辑层 | 用 Async/Await 并发调用多个工具或模型，避免串行等待 |
| 任务层 | 耗时长的任务用消息队列异步处理，并实时推送进度 |
| 交互层 | 打字机效果、预设话术，优化用户感知速度 |

隐藏考点：用户感知速度、Tool Calling 与结果呈现并行化、预加载、推测性采样。术语储备：TTFT、SSE、Async/Await、Celery、RabbitMQ、Tool Calling、Streaming。

### 4. 多 Agent 并发性能和并发控制

**面试官可能怎么问：Multi-Agent 并发执行常见性能问题有哪些？工程上怎么控制并发量？**

答题要点：常见瓶颈包括资源争用、API 限流、token 膨胀、上下文膨胀、调度冲突。控制手段包括队列限流、并发池、优先级、超时重试、幂等、背压、监控告警。答题要结合踩坑和治理。

### 5. Agent 监控和评测指标

**面试官可能怎么问：Agent 运行质量怎么衡量？监控哪些指标？**

答题要点：
- 运行指标：时延 TTFT、任务成功率、工具调用成功率、报错率、重试率、token 成本、任务重复率、状态冲突率、补偿成功率、调度可用性。
- 质量指标：最终产物质量、过程中的报错、人工或自动评估结果。
- RAG 指标：召回率、回答精度。
- 评测方法：固定测试问题，做修改前后结果对比，能定位是检索问题还是生成问题。

## 八、RAG、项目表达与求职准备

### 1. RAG 不等于 Agent

**面试官可能怎么问：你做过 RAG，算做过 Agent 吗？**

答题要点：不能直接等同。RAG 主要是文档问答，Agent 岗位还要工具调用、多步状态管理、失败处理、规划反思。RAG 常见追问包括混合检索怎么做、召回率和回答精度多少、embedding 选型、向量检索与 BM25 权重配比、RRF 融合怎么排序、为什么用 RRF 而不是直接相加相似度分数。RRF 基于排名融合，能避免分数分布和量纲不一致。

### 2. 项目怎么讲

**面试官可能怎么问：介绍一下你的 Agent 项目。**

答题要点：用一段话讲清六要素：处理了什么资料；完成了什么任务；你负责哪一块；发现了什么问题；怎么改的；怎么验证的。更完整的准备用五段式：业务背景、痛点、方案、选型理由、评测结果。常见误区是只堆技术名词，面试官看不出你干了什么。

典型追问：为什么需要 RAG；为什么这里用 Function Calling；为什么任务要拆成多个节点；接口挂了怎么重试；模型输出怎么控制；踩过什么坑，最后怎么解决。

### 3. Agent 学到什么程度能投简历

**面试官可能怎么问：你觉得自己达到投 Agent 岗位的水平了吗？**

答题要点：
- 三样必备：一个相关项目；一份能写清个人情况的简历；一套为项目准备过的技术问题。
- 自测标准：从空白项目开始，给一个真实业务需求，能否在一到两周内独立搭出一个完整能跑的 Agent，并把架构、代码、技术选型、业务价值讲清楚。
- 四条标准：独立完成真实业务场景的完整 Agent 项目，跑通任务理解、拆解、工具调用、获取结果、判断结果、异常处理、输出结果；吃透任务拆解、工具调用、异常处理、结果校验并能解释设计理由；补齐工程基础，包括 API 调用、结构化数据、数据库增删改查、日志排查、部署，RAG、向量数据库、Function Calling、MCP 先会用再深挖；能把项目讲明白。
- 常见误区：学得太散，收藏很多但没有项目；只做简单聊天机器人，简历缺区分度；只做过 RAG 就以为能做 Agent；总觉得自己没学完，不敢投。

### 4. AI 写的项目怎么长期维护

**面试官可能怎么问：用 AI 做出产品后，怎么长期迭代又不把旧功能改坏？**

答题要点：95% 的普通项目用三件套。

| 手段 | 做法 | 作用 |
|---|---|---|
| agent.md | 项目说明文档，写目录结构、技术选型、设计思路，放项目内 | 当项目系统提示词，Agent 读写项目文件时自动加载，每次新会话都知道项目是什么 |
| Git 版本管理 | `git init`，主干维护交付代码，新功能切分支，改好合并回主干 | 改坏能回滚 |
| 测试用例集 | 新功能新增用例，历史用例做回归测试 | 防止加新功能坏老功能 |

Git 是命令行版本管理工具，GitHub 是项目托管平台，能识别 Git 格式并按版本呈现内容。国内网络不便可用 Gitee 替代。复杂项目约 5% 需要额外方案。

# rag-检索与RAG

## 1. Skill 与 RAG 怎么选

**面试官可能怎么问：** Skill 和 RAG 怎么选？什么时候两个都不用？

**答题要点：**
- 一句话记忆：Skill 是知识少到人还能穷举时的 RAG；一个预装，一个查库。
- 选型标准看谁决定装哪份。Skill 由人预先决定，必然生效；RAG 运行时按查询决定，概率命中。内容类型不能作为分工依据。
- 三看效率：份数能否穷举，命中频率，变更频率。
- 一看生死：必须生效还是命中即可。安全红线必须生效，直接写 Skill；产品手册命中即可，用 RAG。
- 兜底原则：能用确定性手段保证的，就别交给概率手段。能写成规则的交给 CI 和静态扫描。
- 标准答案：要 100% 生效给 Skill，要实时可变给 RAG，能写成规则两个都别用。

| 判据 | 倾向 Skill | 倾向 RAG |
|---|---|---|
| 份数能否穷举 | 十几份，人还读得完 | 几百份以上 |
| 命中频率 | 几乎每次都要用 | 偶尔才用到 |
| 变更频率 | 跟着代码发版 | 天天在变 |
| 是否必须生效 | 安全红线必须生效 | 产品手册命中即可 |

**追问：检索调准不就行了？**  
调准的是概率，调不到确定性。六成调到九成五很厉害，但事故要的是百分之百。用概率机制承载必须生效的约束，是设计错误。

**追问：Skill 和 System Prompt 有什么区别？**  
System Prompt 是一次性的，每次对话都得手写；Skill 有触发条件、有版本管理、能跨项目复用。类比手写 SQL 和封装好的存储过程。

**追问：两个一起用呢？**  
可以，而且是常态。Skill 管必须生效的方法论，RAG 管命中即可的事实，两条路最后进同一个上下文。真正的错误是让其中一条去干另一条的活。

**常见误区：** 按内容类型分工；把安全规范随手丢进检索池；全塞进 Skill 导致常驻区膨胀和更新即过期；只做表层检索拼接，不做质量管控。

## 2. 微调、Prompt、RAG 怎么分

**面试官可能怎么问：** 把一份手册丢给 AI，它照着答对了，这算微调吗？微调、Prompt、RAG 怎么分？

**答题要点：**
- 通常不算微调。判断是否微调，关键看模型参数有没有被训练改变。
- 微调是在已有模型基础上继续训练，让相关参数发生调整，把行为固化下来。
- Prompt 是在当次交互中说明要求，不改变模型参数。
- RAG 是在回答前检索资料、补充上下文，通常也不因为这次输入更新模型参数。
- 口诀：提示词交代任务，RAG 补充资料，微调继续训练。三者可以配合，不能互相混叫。

| 维度 | Prompt | RAG | 微调 |
|---|---|---|---|
| 场景类比 | 临时交代这次任务 | 遇到问题先查手册 | 拿一批例子反复做专项练习 |
| 作用时机 | 回答时 | 回答时先检索 | 训练阶段 |
| 是否改变参数 | 否 | 否 | 是 |
| 决定因素 | 当次输入 | 检索到的资料 | 训练样本与训练过程 |

**微调追问：**  
训练后要用没见过的样本检查效果，练过的例子表现好，不代表新问题都能做好。微调不一定改动全部参数，有的方法只训练一小部分参数，或额外加入可训练模块，类似 LoRA 和适配器思路。

**常见误区：** 把“喂资料”叫微调；只看训练集表现；以为微调一定全参数训练。

## 3. RAG 能解决大模型幻觉吗

**面试官可能怎么问：** RAG 一定能解决大模型幻觉吗？

**答题要点：**
- RAG 只能在一定前提下缓解幻觉，不能保证消除。答题结构用“先分情况，再给条件，最后给体系”。
- 理想情况下，检索内容正确，模型被约束为基于给定信息作答，幻觉会降低。
- 两个关键失效机制：召回失效和生成漂移。
- 召回失效包括没搜到正确答案，模型只能自行编造；也包括搜到错误、过时或矛盾信息，模型照着错的答，形成“有依据的错误”。
- 生成漂移是即使检索到正确内容，模型也可能被上下文干扰、自行发挥，甚至把检索内容和参数中的错误信息混合输出。
- 可控的 RAG 需要数据质量、多级召回、生成约束、事实校验共同优化。
- 判断标准：不看有没有接向量库，看检索与生成两个环节的风险是否都被管住。
- 经验数据：AI 生成代码 100 次里有 38 次安全规范没被读进上下文；检索调得再好，经验值约 95%。引用时标注为经验值，面试中最好改用定性表述。

**标准答法四点：**
1. 基础 RAG 只能在一定程度上缓解幻觉。
2. 前提是检索准确、生成严格遵循检索内容。
3. 缺少召回优化与生成校验，RAG 不仅解决不了幻觉，还可能出现“有依据的错误”。
4. 真正可控的 RAG 系统需要数据质量、多级召回、生成约束、事实校验多环节共同优化。

**常见误区：** 直接回答“能”或“不能”；只做表层检索拼接；以为接了向量库就控制住了幻觉。

## 4. RAG 能做统计类问答吗

**面试官可能怎么问：** RAG 找到 10 条退货记录，能不能说总共退了 10 单？

**答题要点：**
- 不能直接拿 Top-K 检索结果计算业务总数。
- 相关性回答和完整性回答要求不同。相关性回答找值得看的材料；完整性回答要求该算的都算进来，漏一笔答案就变了。
- Top-K 是数量上限，不承诺全集。找到 10 条只能证明至少有 10 条。
- 一条记录不等于一个片段。一个订单可能被切成多个片段，10 条检索结果可能反复讲同一笔订单。
- 调大 Top-K 和重排也救不了。上限仍是上限；相似度排序偏向文字像，状态字段标记“退货完成”的记录未必排得靠前；重排只对已取回材料重新排序，不能知道没取回的部分有多少。
- 例外情况：命中的是可信且范围明确的月度报表，可以直接引用总数；问答系统接入了完整数据查询能力，可以先统计再解释。
- 正确链路：业务口径 → 完整只读查询或可信汇总报表 → 带范围的统计结果 → 模型组织回答。

| 问题类型 | 例子 | 本质要求 |
|---|---|---|
| 相关性回答 | 退货流程是什么，找几条尺码不合适的售后案例 | 哪些材料值得看 |
| 完整性回答 | 一共退了多少单 | 该算的是否都算进来了 |

**业务口径要点：**
- 状态口径：“退了”指提交申请，还是退货完成。
- 时间口径：按申请时间划分月份，还是按完成时间。
- 单位口径：一单不等于一行。一笔订单有多个商品明细时，连表后的行数可能把一单算成好几单。按订单标识去重，或直接用一单一行的统计表。
- 月份边界按业务时区确定，包含月初，不包含下月月初。

**技术链路要点：**
- 把问题转成受约束的查询条件。
- 后台执行被允许的只读统计。
- 查询权限与可用字段由后台限制，不能只靠提示词约束。
- 返回值除数量外，还要带时间范围、状态口径、统计对象。
- 分页返回明细时，必须确认全部分页成功结束且未超过服务上限，并按正确标识去重。
- 数据持续变化时固定统计快照，避免翻页过程中前后不是同一批数据。
- 中间某页失败时，不能把已有小计称作总计。
- 抽样数据可以分析，但结论要说明是样本。按语义相似度挑出的几条没有随机样本的代表性。

**金句：** 找到了多少条相关内容，不能直接变成一共发生了多少件。

**常见误区：** 把 Top-K 结果当全量数据；把一条检索结果当一条业务记录；忽略业务口径；用重排解决候选遗漏。

## 5. RAG 入库前怎么清洗

**面试官可能怎么问：** RAG 入库前要做数据清洗吗？清洗和分段是什么关系？

**答题要点：**
- 要做。垃圾不清就分段，等于把垃圾切碎、均匀灌满整个知识库。
- 分段解决“怎么切”，清洗解决“内容里有什么垃圾”。顺序反了，分段规则再好，切出来还是垃圾。
- 脏数据有三类典型风险：结构瑕疵，页眉或标题被切成空段；噪声数据抢占候选名额，目录页、导航页、重复版权行挤掉精准段落；内容错误命中，转换丢行、错字、表格列错位，检索看起来正常但内容是错的。
- 内容错误命中无法靠统计对账发现，只能靠原文件逐段比对和抽样暴露。
- 修错成本随时间指数上升。清洗阶段改一份 markdown 可能几分钟；建库后才发现问题，重建库要几个小时，向量库也可能被污染。

**清洗管线前四步：**
1. 盘点与备份：原始素材原封不动留一份，清洗输出写到另一个目录，永远不覆盖来源文件。
2. 素材预检与分级：检查有没有文本层、垃圾图片比例、碎片化程度、装饰图占比。干净或轻度污染走常规管线；纯扫描件、垃圾图超过三成、碎片特别多，就换源或走重度路线。
3. 格式转换：按格式分三条路线。PDF 和 Office 有文本层直接解析；CHM 和 HTML 手册单独处理；纯扫描件先渲染成图片，再走 OCR 识别。底线是内容不能丢，用成熟工具，脚本只负责编排和后续清洗。
4. 标签清洗：注意标签误删问题。

**数字案例：** 一本计算机网络教程 PDF，604 张图里 84% 是噪声图，未做预检直接跑转换，白跑两轮才发现问题。

**转换三坑：**
- 扫描件空输出不报错。无文本层 PDF 转完输出为空，但不抛错，转换后必须检查空输出标记。
- Excel 合并单元格错位。合并单元格在非首行会输出成空，转换前要解开合并，把首行值填下来。
- 标签误删。清洗标签时用贪婪匹配，会把跨行超长标签中间真正的内容一并删掉，应使用非贪婪匹配并核对。

**常见误区：** 把上传文档、平台自动分段、自动向量化当成完整流程；只做分段不做清洗；覆盖原文件；转换后不检查空输出；Excel 不先处理合并单元格。

## 6. RAG 怎么处理 PDF

**面试官可能怎么问：** 你们 RAG 系统里 PDF 怎么处理？

**答题要点：**
- 只答“解析一下、切块、入向量库”只能拿 60 分。先讲 PDF 的格式本质：Word 存结构，PDF 存排版指令，字是画在坐标上的。
- 一句完整的话在 PDF 里可能是几十个带坐标的小碎片；表格在 PDF 里没有表格对象，只有横线、竖线和散落的字；双栏排版不能直接判断阅读顺序。

**五步处理链路：**
1. 分流：判断文本型还是扫描件。提取字数几乎为 0，或页面全是图片对象，基本可判为扫描件。文本型直接解析，扫描件走 OCR，比如 PaddleOCR。
2. 版面解析：识别哪些是标题、正文，剔除页眉页脚，多栏排版按正确阅读顺序拼回。表格按线条位置把单元格重新框出来，还原成真正的表。主流做法是用版面分析模型，比如 MinerU、Docling。
3. 切分：普通文本按长度切问题不大，表格和图是重灾区。跨页表格被腰斩成两半，检索只能召回一半，模型会看着半张表一本正经地胡说八道。表格整块保留，太大就转成结构化描述再切；跨页段落尽量合并；页眉页脚必须清洗掉。
4. 富内容处理：图表、公式、流程图只提取文字会全部丢失。把整页或图块截图，交给多模态大模型生成文字描述，再把描述与原文一起入向量库。
5. 元数据：每个 chunk 都要带来源文件、第几页、哪个章节标题。企业级 RAG 这是底线，检索后答案才可信，用户才能点回原文。

**真实案例：** 客服支持库导入几百份产品说明书 PDF，用户问“这个型号的功率是多少”，十次有六次答错。根因是参数全在表格里，解析时表格被打散成散字，“功率”和“300 瓦”被切进两个不同 chunk，检索永远只能召回一半。把表格整块还原、单独入库后，准确率立竿见影提升。

**追问：线上效果怎么保证？**  
两个方向：解析质量评估，拿真实文档抽样，检查表格还原是否正确、阅读顺序是否混乱、关键字段有没有丢；检索效果回归，解析改版一次就跑一轮回归测试。线上效果问题往上游追，一半以上最终追到文档解析。

**Java 技术栈工具：** PDFBox、iText、Tika Document Reader；框架侧有 Document Reader、PDF Document Reader、按页读和按段落读的 PDF Reader。

**金句：** RAG 的效果上限，很大程度在文档进库那一刻就定了。

**常见误区：** 不做分流直接解析；整页文字一股脑导出；表格和图按普通文本切；只提取文字不处理图表公式；chunk 不带出处元数据。

## 7. Embedding 原理与选型

**面试官可能怎么问：** Embedding 是什么？在 RAG 里怎么用？相似度怎么判读？

**答题要点：**
- Embedding 是把文本转成向量的过程。文本经过 Embedding 模型后，变成多维空间中的一个坐标，语义相近的文本坐标彼此靠近。
- RAG 中的用法：把用户问题转成向量；与所有文档向量匹配；按相似度确定检索范围；把高分片段交给大模型生成。
- 相似度范围一般为 -1 到 1。越接近 1，向量方向越接近，文本内容相似度越高；接近 0，基本没有关联；为负数，语义差异很大。实操中挑分数高的文本，再做后续筛选。

| 模型 | 特点 | 适用与风险 |
|---|---|---|
| BGE 系列 | 中文上下文表现优秀，开源，可本地化私有部署 | 适合数据不出内网、有合规保密要求的企业 |
| OpenAI text-embedding 系列 | 英文能力也比较强，直接调用 API，无需自行部署 | 需要把数据传给外部服务，有数据出境风险，有出境限制的行业不能用 |

**追问：分词和 Embedding 基础要掌握什么？**  
子词分词常见 WordPiece 和 Unigram。WordPiece 按合并提升似然的子词对构建词表；Unigram 自顶向下裁剪词表。word2vec 是经典词向量框架，包含 CBOW 和 skip-gram，skip-gram 用中心词预测上下文。训练加速常用层次 Softmax 和负采样，层次 Softmax 借哈夫曼树把输出层 softmax 复杂度降到对数级，负采样用少量负样本近似全词表 softmax。

**常见误区：** 只讲接向量库，不讲相似度阈值和分块；把模型对比讲成绝对好坏，实际要看中文能力、合规、接入成本、延迟；把 word2vec 和 skip-gram 并列成两种 Embedding 方法，skip-gram 是 word2vec 内部的一种训练模式。

## 8. RAG 评估怎么评

**面试官可能怎么问：** 给 RAG 做评估，到底评什么、怎么评？

**答题要点：**
- 一条闭环：黄金测试集 → 分层评估 → 指标 → Evaluation Harness → Trace → 修改系统 → 重新评估 → Regression → 新失败回流测试集。
- 测试集是起点。没有可靠的测试集，后续所有指标都失去意义。
- 检索和生成必须拆开测。端到端打分只能告诉你答得不好，分层评估才能定位是没召回、排序不对，还是上下文给了但生成没用上。
- 指标按层归属。检索层看召回和排序相关指标，生成层看忠实度、相关性等指标。具体指标要结合自己项目补充。
- Evaluation Harness 是执行器，放在指标之后，把已经定义好的评估方案自动化跑起来。先想清楚评什么，再解决怎么批量评。
- Trace 放在 Harness 之后、修改系统之前，核心用途是失败归因。Harness 负责发现问题，Trace 负责解释问题。
- 重新评估验证这次修改是否解决了目标问题；Regression 验证修改是否破坏了原本正常的能力。二者缺一不可。
- 新失败回流测试集让测试集持续生长。黄金测试集是持续积累的工程产物，不是一次性静态资产。

**常见误区：** 只做端到端打分；把 Harness 当成评估设计的起点；只重新评估不做回归；测试集一次性构建后不再更新；新失败案例不回流。

# llm-模型原理

> 只保留与 LLM 模型原理和 Agent 面试相关的部分。健身、Word、支付、校园网等与主题无关内容未纳入。

## 1. 上下文窗口的定义与容量误区

**面试官可能怎么问：** 上下文窗口是什么？窗口越大越好吗？

**答题要点：**
- 上下文窗口是模型最大单次输入加输出 token 总量，相当于模型的瞬时记忆容量。
- 窗口大能容纳更多文档、对话、知识库内容；窗口小需要频繁分片、分段、多轮拼接。
- 日常短对话小窗口够用；长文档摘要、代码解析、超长报表分析需要大窗口。
- 核心误区：容量不等于有效记忆能力。能装进去，不代表模型能有效利用。
- 工程结论：够用即可，优先小窗口、分片加 RAG、记忆压缩，避免无脑堆长文本。

## 2. 窗口扩容的四大代价

**面试官可能怎么问：** 为什么上下文窗口不是越大越好？

**答题要点：** 按效果、结构、成本、可靠性四个维度组织答案。
- 注意力稀释：输入越长，注意力资源越分散，关键信息被淹没，核心规则识别失效。
- 位置编码偏移：超长上下文会出现位置泛化失效，表现为首尾遗忘、中间错乱，即迷失在中间。
- 推理成本暴涨：Transformer 推理复杂度与文本长度呈平方级关系，窗口翻倍，显存占用和推理耗时显著上涨，线上并发难以承受。
- 幻觉概率上升：超长文本中模糊、冗余、冲突内容多，模型更容易脑补拼接错误信息。

## 3. 长上下文踩坑案例与知识库选型

**面试官可能怎么问：** 知识库为什么不直接用百万级长上下文模型？长上下文有什么真实风险？

**答题要点：**
- 可讲文档 AI 总结案例：把整本手册一次性丢入百万级长上下文模型，开头关键规则被遗忘，中间内容错乱，结尾回答张冠李戴。
- 归因是上下文稀释、位置偏移、漂浮注意力。盲目堆长度，准确率反而暴跌。
- 知识库问答优先 RAG 分片检索，只召回相关片段、过滤冗余内容，不用超长上下文兜底。
- 面试可补一句：长上下文和 RAG 各有适用边界，业界仍有分歧。

## 4. 按场景选窗口的对比表

**面试官可能怎么问：** 实际项目怎么选上下文窗口方案？

**答题要点：** 先判断任务对记忆深度和成本敏感度的要求，再选窗口规格。

| 场景 | 推荐方案 | 理由 |
|---|---|---|
| 短任务、高频问答 | 小窗口高速模型 | 延迟低、成本低、准确率高 |
| 长文档解析，如合同审核、代码分析 | 适量大窗口加分片加重排 | 不盲目一次性灌入全文 |
| 知识库问答 | 优先 RAG 分片检索 | 只召回相关片段、过滤冗余内容 |
| 多轮长对话 | 记忆压缩、摘要沉淀 | 清理无效历史，避免上下文堆积过载 |

## 5. 长上下文和多轮对话的优化手段

**面试官可能怎么问：** 超长上下文遗忘、位置偏移怎么解决？多轮长对话怎么控制上下文？

**答题要点：**
- 上下文滑动窗口：只保留最近有效对话，淘汰老旧无效内容，控制输入长度。
- 记忆摘要压缩：长对话定时总结，用摘要替代原始冗长内容，节省窗口空间。
- 稀疏注意力优化：降低超长文本算力消耗，提升长文本推理速度。
- 分段推理加结果融合：长文档拆分多段推理后合并结果，规避偏移与稀释问题。
- 答题层次：先说选型，再补实现手段。

## 6. 对话记忆机制：旧方案为何干扰新指令

**面试官可能怎么问：** 为什么改了需求 AI 还沿用旧方案？是模型不听话吗？

**答题要点：**
- 模型看到的不只是最后一句，系统会把历史聊天压缩打包成上下文，连同新指令一起送入模型。
- 聊得越久历史包袱越重。作废内容仍属于历史上下文，没有被真正剔除。
- 旧方案占大量篇幅和权重，新指令只有一两句，容易被淹没。有限上下文里，篇幅是权重的粗粒度代理。
- 解法：不要在旧窗口反复纠正；让 AI 提炼有效需求，生成完整提示词，开新窗口重新开工。
- 通用心智：遇到 AI 反常输出，先问它在机制上看到了什么，再决定怎么改输入。

## 7. Agent 基础面试自查框架

**面试官可能怎么问：** 一个标准 Agent 由哪些核心模块组成？各模块解决什么问题？

**答题要点：**
- 整体架构：记忆、工具调用、规划、反思、ReAct 等核心模块。
- 记忆模块：区分短期记忆和长期记忆。
- 工具调用模块：Agent 区别于纯对话模型的关键。
- 规划模块：任务分解与主流规划策略。
- ReAct：核心思想及其对 Agent 的重要性。
- Self-Reflection：作用，以及去掉会带来哪些问题。
- 复杂任务优势：Agent 相比普通大模型直接问答强在哪里。

**工程细节追问：**
- 工具解析模块一般做哪些事，会遇到哪些典型故障。
- 记忆存储选型：内存和向量库各自适用场景。
- 工具数量太多会出现什么现象，涉及工具选择与调用约束。
- Temperature 对工具调用效果的影响，过高过低分别怎样。
- 多轮任务中上下文窗口溢出如何产生，造成什么后果。
- Agent 预训练与微调的设计思路，以及和 Prompt 驱动 Agent 的本质区别。

**核心概念追问：**
- 能力归因：Agent 能力强弱取决于大模型本身还是 Agent 框架，二者本质区别、谁是瓶颈。
- 多 Agent 系统的定义与典型业务场景。
- 微调为什么需要大量样例数据，样例不足会带来什么问题。
- Agent 场景下如何理解过拟合，工程上如何观察判断。
- Agent 推理运行指什么过程，与微调训练的区别。
- 涌现行为如何理解，并举实际例子。
- 增加工具数量、增加智能体数目是否带来线性提升，对业务开发有什么指导意义。
- 答题要求：不要只背定义，要能回答为什么、去掉会怎样、实际会遇到什么问题。

## 8. 常见误区与答题结构

**面试官可能怎么问：** 大模型原理类面试怎么答得有体系？

**答题要点：** 推荐顺序如下。
1. 先否定绝对化结论：不是越大越好，要结合业务权衡。
2. 给定义并区分概念：窗口等于输入加输出 token 上限，容量不等于有效记忆。
3. 列代价：注意力稀释、位置偏移、成本平方级增长、幻觉上升。
4. 给场景方案：短问答用小窗口，知识库用 RAG，长对话做压缩。
5. 补优化手段：滑动窗口、摘要压缩、分段推理融合。

**常见误区：**
- 只背名词，不解释模块存在的意义。
- 只堆窗口长度，不会分片、压缩、精准召回。
- 把 AI 反常输出归因为模型笨，不分析上下文机制。

**可用话术：**
- 新手只会堆窗口堆长度，资深开发懂得取舍：分片、压缩、精准召回。
- 线上 AI 项目准确率低、延迟高、成本爆炸，很多是因为无脑使用超长上下文。

## 9. 追问准备与评测

**面试官可能怎么问：** 有效记忆能力怎么衡量？位置编码偏移还能怎么深入？

**答题要点：**
- 可用“大海捞针”类长上下文基准评测有效记忆能力。
- 位置编码可延伸 RoPE 外推、位置插值。
- 成本量化可用具体 token 数与显存、延迟数据，把平方级增长讲成可感知的数字。
- Agent 题库标题提到 Transformer，但内容聚焦 Agent，Transformer 底层需另补注意力机制、位置编码、训练与推理等知识。

# prompt-提示词工程

## 一、长任务里 Agent「忘了」的两种原因

**面试官可能怎么问：长任务中 Agent 经常表现得像忘了前面的内容，你怎么分析原因？**

答题要点：先拆成两个性质不同的问题，再分别给对策。

| 维度 | 上下文溢出 | 上下文腐化 |
| --- | --- | --- |
| 本质 | 输入超出窗口容量，装不下 | 信息装得下，但读取质量下降 |
| 成因 | 每轮回复和工具结果都进入后续请求，轨迹持续增长 | 大量无关记录和重复内容干扰读取，早期目标与约束找不回来 |
| 表现 | 请求失败或被截断 | 决策质量下降，偏离原始目标 |
| 对策 | 压缩、隔离、外置存储 | 提炼摘要、清理噪声、保留决策约束 |

关键结论：窗口更大并不保证长任务可靠，容量够也会腐化。

**面试官可能怎么问：上下文快满了，模型会有什么异常行为？**

答题要点：模型可能判断窗口快耗尽，在任务尚未完成时提前收尾。这是长任务里容易被忽略的隐性风险，做 Agent 产品时要专门防。

## 二、压缩到底在做什么

**面试官可能怎么问：上下文压缩是不是就是把历史消息删短一点？**

答题要点：压缩的关键是提炼。把分散的记录整理成三类内容：已确认的事实、尚未解决的问题、下一步需要的信息。用提炼后的表示替换大段原始记录，这个转换是有损的，所以要设计好保留什么。

**面试官可能怎么问：压缩摘要必须保留哪些信息？**

答题要点：五类核心信息缺一不可。

1. 任务目标
2. 关键决策约束及其背后理由
3. 失败路径
4. 信息来源
5. 进展脉络

丢掉失败信息，后面就不知道做过什么、为什么失败；保留来源和线索，需要时还能回查原始记录。

**面试官可能怎么问：怎么判断一次压缩做得好不好？**

答题要点：压缩成功不等于字数变少。判断标准是后续行动是否仍有充分且可核查的依据。字数只是副产品。

## 三、工程代价与触发策略

**面试官可能怎么问：做上下文压缩会带来什么成本？**

答题要点：

- 压缩发生在两次模型调用之间，由框架整理下一轮消息，不占用模型推理。
- 稳定的系统指令与工具定义尽量不改，保证前缀可复用。
- 历史工具结果被摘要替换后，替换位置之后的缓存需要重建，此前的相同前缀仍能复用。等于用一次重建代价换后续负担减少。
- 推论：不要每轮随意改写历史，改写越频繁，缓存命中越差。

**面试官可能怎么问：压缩什么时候触发？阈值怎么定？**

答题要点：一个可用的实验配置是窗口使用率超过 80% 时，批量压缩尚未处理的工具结果，并打上压缩标记避免反复处理。80% 只是该实验的取值，实际阈值要结合任务类型和预算调，面试时要说明这是可调参数而非通用答案。

## 四、比压缩更结构化的两种手段

**面试官可能怎么问：除了整体压缩，还有什么办法控制上下文成本？**

答题要点：两种。

分层处理，按信息的价值和生命周期分开对待：

- 大体积输出存磁盘，模型先看预览
- 低价值噪声直接移除
- 每轮保留结构化摘要，记录逻辑脉络
- 必要时再做完整压缩

核心逻辑是不同信息的价值和生命周期不同，关键决策不能和网页噪声一起被丢掉。

子 Agent 隔离，在信息进入主轨迹之前就拦住：独立子 Agent 在自己的上下文里完成探索，只把结论摘要返回主 Agent，大量中间记录不进入主上下文。代价是子 Agent 看不到主 Agent 的完整背景，所以派发任务时描述必须清楚、自包含。

## 五、答题时的常见误区

**面试官可能怎么问：说说你对长上下文 Agent 可靠性的理解。**

容易踩的坑：

- 把溢出和腐化混为一谈，只答「窗口不够大」
- 认为换更大的窗口就解决问题，忽略腐化
- 把压缩等同于删字或截断，说不出保留清单
- 用「字数变少」当压缩成功的标准
- 忽略缓存重建代价，主张每轮都改写历史
- 把某个具体阈值当成通用结论
- 用子 Agent 隔离时忘了任务描述要自包含

收尾可以用一句话总结：让下一轮看到充分而清楚的信息，才是长任务保持连续的关键。

| 步骤 | 核心动作 | 产出与标准 |

| 1 公司信息 | 查成立年份、企业文化与价值观、重大事件与产品信息 | 能回答“你了解我们公司吗”，并判断公司发展阶段和稳定性。检索可用 AI 工具，快速够用 |
| 2 拆解 JD | 从 JD 筛 3 到 5 个能力关键词 | 产品经理示例：需求拆解、项目推进、用户思维、数据分析、商业敏感。后续项目、自我介绍、优缺点都回扣这些词 |
| 3 改造项目 | 选 1 到 2 个最匹配关键词的项目，用 STAR 重写 | STAR 四要素：背景、任务、行动、结果。自检标准：一句话能把项目讲清楚 |
| 4 搜高频考题 | 牛客网、小红书搜“公司名 + 面经”“岗位 + 高频考题” | 用 AI 起草答案，再改成自己的项目细节并背熟，避免背出来像模板 |
| 5 准备三类常见问题 | 自我介绍、为什么来这家公司、优缺点 | 见下一节答题要点 |
| 6 半小时串讲 | 把公司信息、关键词、项目故事、题库答案、常见问题串成整体 | 准备包能连续讲述，避免散点堆叠 |

顺序逻辑：先公司，再岗位，再自己，再题库，再常见问题，最后整合。

## 2. 高频问题：面试官怎么问，怎么答

| 面试官可能怎么问 | 答题要点 |
|---|---|
| “你了解我们公司吗”或“为什么来我们公司” | 说成立年份带来的发展阶段和稳定性判断，提企业文化与价值观匹配，提近期重大事件和产品。再表达强烈求职意愿和在该行业深耕的意愿 |
| “你为什么适合这个岗位” | 先复述从 JD 提取的 3 到 5 个关键词，再逐项给项目证据。自我介绍、项目、优缺点都围绕这些能力项 |
| “请先做个自我介绍” | 控制在 1 到 2 分钟，按 JD 关键词组织，用 1 到 2 个项目经历做证据，避免逐条念简历 |
| “讲一个最有代表性的项目” | 选 1 到 2 个最匹配岗位关键词的项目，按 STAR 讲背景、任务、行动、结果。练到一句话能概括 |
| “说说你的优缺点” | 优点和缺点都选与岗位核心能力相关的。回答落点是这些特点给工作带来加成还是可能造成阻碍，以及怎么规避 |

## 3. 专业题框架：以“几百只怪物怎么优化”为例

面试官可能怎么问：几百只怪物同屏怎么优化？项目卡顿怎么优化？

答题顺序：先定位瓶颈，再降低逻辑计算，再削减画面开销，最后同条件复测。不要一上来报对象池、多线程、降面数。

| 步骤 | 答题要点 |
|---|---|
| 定位瓶颈 | 在目标设备用性能分析工具，看时间花在算行为、做碰撞，还是画模型、画特效。区分持续卡，还是刷怪、放技能时突然卡一下 |
| 降低逻辑计算 | 近身战斗的怪物及时更新，远处怪物降低判断频率。寻路不必每帧重算，目标明显移动或原路线失效时再更新。分批错峰处理，避免几百只怪物同一帧一起干活。范围检测按区域管理，先取附近候选再精确判断。正在攻击玩家的怪物，攻击判定和碰撞不能省 |
| 削减画面开销 | 按距离和屏幕占比做 LOD，远处用低精度模型并降低骨骼动画更新频率。检查不可见对象是否还有不必要的渲染、阴影和动画开销。逻辑与渲染分离，不可见不代表逻辑能全部停掉。限制同屏特效、灯光、阴影数量，保住关键攻击提示，弱化次要效果 |
| 同条件复测 | 回到同一台设备、同一个场景，对比帧耗时和卡顿峰值。不能这次测 100 只、下次测 50 只就宣称性能提升一倍 |

面试讲述模板：你发现了什么瓶颈，为什么用这个办法，优化后怎么验证。

## 4. 常见误区与加分点

| 面试官追问或常见误区 | 答题要点 |
|---|---|
| “对象池能解决吗” | 对象池主要减少反复创建和销毁的开销。如果卡顿发生在怪物存活期间，加对象池不一定明显改善。能讲清适用边界是加分项 |
| “降频会不会影响战斗” | 降低的是不必要的计算。正在攻击玩家的怪物，攻击判定和碰撞不能随便省，否则帧率上来了，战斗却不对劲 |
| “看不见的怪物能全停吗” | 不可见对象要检查渲染、阴影、动画开销，但逻辑与渲染要分离，不可见不代表逻辑能全部停掉 |
| “优化后怎么证明有效” | 同一台设备、同一个场景复测，比较帧耗时和卡顿峰值。测试条件要一致 |
| “AI 生成的答案能直接背吗” | 先搜真题再用 AI 起草，之后要替换成自己的项目细节，否则容易像模板 |
| “公司调研要做多深” | 快速够用，重点放在 JD 关键词和项目证据。公司信息能支撑“为什么来”和“你了解我们吗”即可 |

## 5. 一页速记

- 六步 SOP：公司信息 → JD 关键词 → STAR 项目 → 高频考题 → 三类常见问题 → 半小时串讲
- 关键数字：JD 提取 3 到 5 个关键词，准备 1 到 2 个项目，自我介绍 1 到 2 分钟，串讲 30 分钟，复测同设备同场景
- 性能优化四步：定位瓶颈 → 降低逻辑计算 → 削减画面开销 → 同条件复测
- 专业题表达模板：发现瓶颈 → 为什么用这个办法 → 优化后怎么验证
- 三类必背问题：自我介绍、为什么来这家公司、优缺点
