## 直接复制以下内容给豆包 👇

我补充一下我们项目的具体形态，请基于这些信息重新审视你之前的建议。

### 一、我们在做什么：不是"通用 AI 助手"，而是**应用内嵌的任务型 Agent**

产品叫 VidInsight（赛博大胃袋），是一个**Windows 桌面软件**（Tauri 2 外壳 + 本地 Python FastAPI 后端作为 sidecar 进程），**纯本地运行、无云端依赖**（用户数据存本地 SQLite）。

它的业务是：用户贴一条短视频链接（B站/小红书/抖音/YouTube），系统自动**下载 → 提取音频 → 语音转写 → 用 LLM 生成结构化洞察报告**；报告入库后，用户可以**继续追问**（基于已生成报告做 RAG 问答）。

**所以我们的 Agent 有两类任务，这是关键特征**：
1. **生产（produce）**：把一条新链接变成一份洞察报告（调工具触发长流程：下载/转写/生成）
2. **消费（consume）**：在已有报告里检索并回答用户问题（RAG）

这两类**跑在同一个 ReAct 环里**，由意图分类决定走哪条路。

### 二、Agent 的具体实现（技术事实）

**架构**：自研 ReAct 循环（不是 LangChain / AutoGPT 这类框架搭的），感知→决策→行动→反馈闭环。

**工具集（共 8 个，分两类，这是我们的设计特色）**：
- **消费类 4 个**（普通权限）：`search_kb`（检索知识库）、`get_source`（取原文出处）、`list_notes`（列出已有笔记）、`clarify`（信息不足时反问用户）
- **生产类 4 个**（**受限权限**，会触达外部平台或产生长任务）：`generate_note`（触发完整生成管线）、`parse_video_link`（解析链接元信息）、`parse_xhs_note`（小红书笔记解析）、`ingest_board`（收藏专辑入库）

**"受限工具"是我们特意设计的纪律**：这 4 个工具会消耗大量资源或触达第三方平台，所以设了白名单机制——不是任何请求都能调，避免 Agent 乱触发长任务。

**循环约束**：
- 最多 **8 轮**（MAX_ROUNDS=8），超限就基于已有信息回答并说明限制，**不无限循环**
- **工具异常不终止轮次**：任何工具失败都返回结构化结果 `{success: false, reason, recoverable: true}` 回灌给模型，让模型自己决定下一步——失败信息是决策输入，不是终止信号
- 每次调用都写**可回放轨迹**（`traces/*.jsonl`：start → llm/tool×N → final），可复盘每一步

**输入安全层**：`_sanitize_input()` 有 22 组正则过滤（ChatML/Llama 分隔符、中英文指令注入、角色扮演劫持、提示词提取），超 4000 字符截断——恶意载荷在进入意图分类之前就被挡住。

**反幻觉**：系统提示词强制要求回答带 `[n]` 来源编号，绑定到具体视频/时间戳；找不到依据时必须明确说"不知道"，不许编。

### 三、我们给自己的定位：**Agent + Harness 双层**

我们特意区分了两个概念（这点如果理解偏差，建议会跑偏）：

- **Agent** 决定"下一步做什么"（推理、选工具、组织答案）
- **Harness** 规定"它在什么边界里做、怎么记录、怎么验证、什么时候算真的完成"

我们把它拆成 6 层边界：
1. **Input Harness** — 注入过滤、长度截断、意图分类
2. **Context Harness** — 预检索注入、来源编号、上下文裁剪
3. **Tool Harness** — 工具白名单、JSON Schema 校验、8 轮上限
4. **Runtime Harness** — 任务串行队列、协作式取消（用户能中途取消）
5. **State Harness** — status.json 状态机、checkpoint 断点续跑、DAO 持久化
6. **Safety Harness** — 伦理约束、红线校验

### 四、我们的工程约束（会影响你给建议的方向）

1. **纯本地、无云**：不能建议"接入云向量库/云记忆服务"
2. **答辩要现场实测**：稳定性 > 新功能。任何建议必须"当天能演示"
3. **依赖外部 LLM 服务**（通过 OpenAI 兼容接口，可能是本地反代）：上游会挂，必须有降级（我们已实测：上游持续 503 时 164 秒内给出明确失败答复）
4. **产品红线**：对第三方平台只做**被动读取**——绝不自动登录、绝不自动导航爬取。所以任何"让 Agent 自动去平台操作"的建议都不可用
5. **团队规模**：学生项目，1-2 人开发，没有 DevOps/运维资源

### 五、我现在最想让你帮我判断的问题

1. 我们的 Agent 设计里，**哪一层是最薄弱的**？（我自己怀疑是"上下文管理"——现在只是简单截取历史 + 检索结果裁剪，没有做 dsh 那种三级压缩）
2. **8 轮上限**是否合理？还是应该改成动态的（比如按 token 预算而不是轮数）？
3. "生产类受限工具"这个设计，在 Agent 安全上算不算一个好的实践？有没有更标准的做法？
4. 我们**没有长期记忆**（跨会话记忆用户偏好），这对一个"内容洞察工作台"算不算硬伤？还是说属于可延后项？

### 附：我用自己项目实测了那几个模型的真实表现（供你参考修正）

你之前给过 GLM-5.3 / GLM-5.3-Flash / DeepSeek-v4.1-Flash / Hy4-preview 的横向对比（按"代码 Agent"排序）。我用**我们项目的真实任务**实测了这几个模型，结论和你的排序**不一致**，贴给你参考：

**测试任务**（都是我们 Agent 的实际工作）：
- 任务1：Function Calling —— 给一个检索工具，看模型是否正确调用
- 任务2：结构化 JSON 输出 —— 要求输出含 5 个固定键的报告结构

| 模型 | 工具调用 | 结构化输出 | 单次耗时 | 实测结论 |
|---|---|---|---|---|
| deepseek-v4.1-flash | ✓ 正确调用 | ✓ 5 键齐全 | **2.7s** | **最均衡，适合做主力** |
| glm-5.3 | ✓ 正确调用 | ✓ 5 键齐全 | 3.9s | 稳，但更慢 |
| glm-5.3-flash | ✓ 正确调用 | ✓ 5 键齐全 | 6.0s | 可用 |
| hy3-c | ✓ 正确调用 | ✓ 5 键齐全 | 1.9s | **最快，性价比高** |
| hy4-preview | ✓ 正确调用 | **✗ 失败** | **76s** | **重思考模型：6829 字思考链把 token 预算吃光，正文一个字没输出** |

**关键发现**：你排第一的 Hy4-preview 在我们任务上**最不可用**——它属于"重思考"模型，思考链极长，做结构化输出时容易把预算耗在思考上，正文空手而归。而这类模型恰恰不适合我们这种"要稳定输出固定结构"的任务。

**所以我想问的第 5 个问题**：对"固定结构化输出"这类任务，是不是应该**避开重思考模型**、优先选 flash 类？我们现在的默认模型选型对不对？

## 我（ZCode）对这份补充说明的判断

**为什么这样写**：豆包不知道我们是什么 Agent，所以最容易犯的错是给出"通用 Agent 建议"——比如推荐接 LangChain、推荐云记忆、推荐多 Agent 协作、推荐自动浏览器操作。这四类建议对我们**全是错的**（分别是：我们已自研 ReAct 不需要框架、我们纯本地不能上云、1-2 人做多 Agent 是浪费、自动操作违反产品红线）。

所以补充说明里我特意加了**第四节"工程约束"**——把会让建议跑偏的边界先划掉。

**第五节我列的 5 个问题，是我们真实存在的短板**（第 5 个是实测后新加的）：
- 上下文管理：确实只做了简单截断（记忆里也记着"dsh 式三级压缩未做，属 DVT 量级"）
- 8 轮 vs token 预算：这是个真问题，轮数上限对长任务不友好
- 受限工具设计：这是我们的特色，值得外部验证
- 长期记忆：确实没有，需要判断优先级
- 模型选型：实测发现"重思考模型不适合结构化输出"，需要确认默认选型

**如果你想让豆包给更有价值的回答**：把它当"架构评审员"用（问"哪层最薄弱"），而不是当"需求分析师"用（问"我该做什么功能"）——因为我们的功能范围在 EVT 阶段已经冻结了。

**顺带修掉一个真 bug**：我上次同步 WorkBuddy 模型时，照抄了 ZCode 侧的 `hy4-preview-f`，但实测发现**该模型在我们池里根本不存在**（用户选中会直接报 `pool_empty`）。已改为池中真实可用的 `hy4-preview`，并把 DB 里的残留清掉。
